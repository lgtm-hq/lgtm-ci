# Upgrading to v0.111.0: each reusable accepts only its own egress presets

Applies to callers that pass `egress-preset`, or one of the per-job preset
inputs (`egress-build-preset`, `egress-deploy-preset`, `test-egress-preset`),
to a reusable workflow (#1623). Callers that leave those inputs at their
defaults have nothing to do.

## What changed

Up to v0.110.x every reusable embedded every egress preset, so any preset
name from `scripts/ci/lib/egress/presets.sh` worked with any reusable. From
v0.111.0 a reusable embeds only the presets it declares on its
`# lgtm-ci-egress-accepts:` line: the default of each preset input, plus any
fixed preset one of its jobs selects. Any other name finds no entry, and the
job fails at its `Fail on unknown egress-preset` step, as a misspelt name
always has:

```text
::error title=unknown egress-preset::not a preset - 'github-tooling'
```

With an accepted preset, each job may reach exactly the hosts it reached
before.

## Are you affected?

You are affected if a `with:` block passes a preset name that is not in the
reusable's row below. Each of these, for example, now fails:

- `egress-preset: github-tooling` to `reusable-release-version-pr.yml` (the
  previous starter example);
- `egress-preset: rust-release` to `reusable-build-artifact.yml`;
- `egress-preset: build-artifact` to `reusable-test-rust-build.yml` or
  `reusable-rust-build.yml`, whose default `quality` already holds every
  `build-artifact` host except `nodejs.org`;
- `egress-preset: pypi` or `github-tooling` to `reusable-test-node.yml`;
- `egress-preset: github-tooling` to `reusable-test-python.yml`.

To check before you move a pin, compare each preset you pass with the
reusable's `egress-preset` input description, which names the accepted
presets, or run this in a checkout of the new release:

```bash
bash scripts/ci/egress/sync-workflow-presets.sh --accepted .github/workflows/<reusable>.yml
```

One case does not fail: `replace` mode (the default) with a non-empty
`allowed-endpoints` never reads the preset, so a name the reusable does not
accept passes unnoticed. Drop the input anyway; it does nothing there.

## What to do instead

Drop the preset input to get the default preset. If the job needs hosts the
default preset lacks, list them in `allowed-endpoints` and set
`allowed-endpoints-mode: append`; they are added to the default preset. Name
each host exactly. Do not use a wildcard on a domain anyone can register a
name under, such as `*.blob.core.windows.net` or `*.amazonaws.com`.

```yaml
# Before: fails from v0.111.0
with:
  egress-preset: rust-release
# After: the default preset plus the hosts the build needs
with:
  allowed-endpoints-mode: append
  allowed-endpoints: >-
    ghcr.io:443 pkg-containers.githubusercontent.com:443
    docker.io:443 registry-1.docker.io:443 auth.docker.io:443
```

To see which hosts a preset adds over a reusable's default, compare the two
in `scripts/ci/lib/egress/presets.sh`:

```bash
source scripts/ci/lib/egress/presets.sh
comm -23 <(egress_preset_endpoints rust-release | sort -u) \
  <(egress_preset_endpoints build-artifact | sort -u)
```

The Rust cross-build example in
[reusable-workflows.md](../reusable-workflows.md) lists every host `cross`
needs on `reusable-build-artifact.yml`.

## Accepted presets per reusable

Generated with `sync-workflow-presets.sh --accepted` for v0.111.0. All preset
inputs of one reusable accept the same set. For a later release, read the
reusable's input description: `sync-workflow-presets.sh --check` keeps it
equal to the declaration.

`reusable-main-failure-notifier.yml`, `reusable-publish-rust-release.yml` and
`reusable-release-failure-notifier.yml` have no preset input; their jobs use
the fixed presets listed. `reusable-docker.yml`,
`reusable-docker-multiplatform.yml`, `reusable-release-recover.yml` and
`reusable-rust-build.yml` forward `egress-preset` to the reusables they call,
and a contract test checks that the callee accepts every preset the caller
does.
