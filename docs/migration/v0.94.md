# Version-PR token permissions (next feature release)

Applies to `reusable-release-version-pr.yml` and
`reusable-release-multi-ecosystem.yml` (#1449).

The `version-pr` job's App token used to request no permissions, so it carried
everything the release App holds on the repository. It now requests
`contents: write`, `pull-requests: write` and, by default, `workflows: write`.
Other permissions the App holds no longer reach this job.

## What to do

**The App holds `Workflows: Read and write`** (the documented setup in
[onboarding](../onboarding.md#release-workflows-github-app-and-secrets), and
already required by `reusable-release-auto-tag`): nothing. Check that the
installation has accepted the permission:

```bash
gh api /orgs/<org>/installations \
  --jq '.installations[] | select(.app_slug=="<app-slug>") | .permissions'
```

**The App does not hold it:** the `version-pr` job now fails at
`Create GitHub App installation token` (HTTP 422, "The permissions requested
are not granted to this installation"). Either grant the permission and accept
it on the installation, or opt out by adding the input to the existing call:

```yaml
with:
  request-workflows-permission: false
```

## Behaviour with `request-workflows-permission: false`

The token carries `contents: write` and `pull-requests: write` only. A new
step, `Refuse workflow file changes`, runs after the ecosystem or manifest
updaters and the `version-update-script` diff are applied, and before the
version PR is created. It fails the job when any changed path is under
`.github/workflows/`: modified, staged, untracked, deleted, or either side of
a rename. The error names each path and says to set
`request-workflows-permission: true` and grant the App
`Workflows: Read and write`.

A caller whose version bump edits a workflow file, for example a `manifests`
key or an ecosystem path under `.github/workflows/`, cannot use `false`.

### Callers that pin `tooling-ref`

The new step runs a script that first ships in this release. A caller that
sets `request-workflows-permission: false` and also pins `tooling-ref` to an
older commit does not have it:

- Without `tooling-ref-allow-divergence`, the existing divergence guard
  already stops the run.
- With `tooling-ref-allow-divergence: true`, the step fails with Python's
  "can't open file" error. Nothing is published.

Remove the `tooling-ref` override, or move it to this release or newer,
before setting the input to `false`.

## Leftover version-PR branches with `false`

A version PR that is closed without merging leaves its branch behind. If
workflow files then change on the default branch and the next run computes the
same version, the job force-moves that branch across the workflow diff. The
concern was that GitHub would refuse that update for a token without
`workflows: write`, as it does for a floating tag pushed with git (#698).

A live run on the external fixture did not reproduce it: with `false`, the job
moved a leftover branch across a workflow file that had been added on the
default branch, and opened the version PR. That is one configuration:
github.com, commits created through the API, and a workflow file added rather
than modified or deleted. If the job fails on the branch update in another
configuration, delete the leftover version-PR branch and rerun.

## What was verified live, and what was not

Verified on the external fixture with the narrowed token: creating the signed
version PR, creating and applying a label that did not exist, assigning the
individual CODEOWNER and requesting their review, and both values of
`request-workflows-permission`.

Not verified live:

- **Auto-merge** (`auto-merge: true`). It needs contents and pull-requests
  write, which the token requests. A failure is loud and leaves the version PR
  open for a manual merge.
- **Merge queue.** The queue lookup treats a failed query as "unknown" and
  skips the branch update with a notice instead of failing the job. If version
  PRs stop updating on a repository with a merge queue after this upgrade,
  check that notice.
- **An App without `Workflows: Read and write`, default setting.** GitHub
  documents that a token cannot request more than the App holds, so the mint
  fails before anything is published. The exact error text is not confirmed.

## Also in this change

- Any step that used the `version-pr` token for something outside contents,
  pull requests and workflows loses that access. No lgtm-ci step does.
- `runner-governor.yml` stays the one App token mint without `permission-*`
  keys, because the action has no input for the organisation Variables
  permission. It is lgtm-ci's own workflow and no caller is affected.
