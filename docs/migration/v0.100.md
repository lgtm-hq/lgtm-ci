# Upgrading to v0.100.0: `reusable-release-multi-ecosystem.yml` is removed

Applies to callers of `reusable-release-multi-ecosystem.yml` (#1356). The
workflow was a `preview` entry with no known consumer, and
`reusable-release-version-pr.yml` now takes all of its inputs (#1546), so it
is deleted without a deprecation release. A pin to this release or later that
still calls it fails with a `startup_failure`, because the file no longer
exists. No other caller has anything to do.

## Migrating to `reusable-release-version-pr.yml`

Change the `uses:` line and drop `job-name`. Everything else stays as it is:

```yaml
jobs:
  version-pr:
    uses: lgtm-hq/lgtm-ci/.github/workflows/reusable-release-version-pr.yml@<sha> # vX.Y.Z
    permissions:
      actions: read
      contents: write
      issues: write
      pull-requests: write
    with:
      manifests: '{"package.json":"npm","VERSION":"raw"}'
      # bump, version, prerelease-tag, changelog and every other input: as before
    secrets: inherit # or the four secrets by name, as before
```

### Inputs

Every input except `job-name` exists on version-pr with the same name and
type, and the same default except `manifests` (see below). The same four
secrets (`RELEASE_APP_ID`,
`RELEASE_APP_CLIENT_ID`, `RELEASE_APP_PRIVATE_KEY`, `LGTM_CI_TOOLING_TOKEN`)
are accepted. The outputs are the same.

- `job-name` is dropped. Version-pr's job name is fixed at `Create Version PR`
  so that a skipped job still reports that check.
- `manifests` is optional on version-pr and defaults to empty, which skips the
  manifest update. The removed workflow required it and failed when it was
  empty. On version-pr, an empty `manifests` with no `ecosystems` and no
  `version-update-script` opens a changelog-only version PR, so make sure the
  value you pass is never empty (for example when it comes from a variable).

Version-pr also takes `ecosystems`, `ecosystem-config` and its other optional
inputs. Their defaults leave them off, so leaving them out keeps the behaviour
you had.

### Check names

With the default `job-name` (`Create Version PR`) the check names do not
change: `Prepare version update hook`, `Run version update hook`,
`Create Version PR` and `Report release automation failure`. A caller that
passed another `job-name` gets `Create Version PR` instead, so update any
branch protection or ruleset that requires the old name.

### Artifacts, concurrency and failure issues

These now use version-pr's names:

- Artifacts: `release-multi-ecosystem-{metadata,tooling,hook-changes}-<key>`
  become `release-version-pr-{metadata,tooling,hook-changes}-<key>`.
- The `version-pr` job's concurrency group:
  `reusable-release-multi-ecosystem-<repository>` becomes
  `reusable-release-version-pr-<repository>`.
- The failure-report key: `release-multi-ecosystem` becomes
  `release-version-pr`.

A new failure files or updates an issue under `release-version-pr`. An issue
still open under `release-multi-ecosystem` is never touched again; close it by
hand.

The artifact key comes from `tag-prefix`. A workflow run that calls
version-pr twice (for example once for the former multi-ecosystem call and
once for an existing version-pr call) must give the two calls different
`tag-prefix` values: the uploads use `overwrite: true`, so with the same
prefix one call's hook-changes diff can replace the other's before
`version-pr` downloads it. The two calls also share one concurrency group per
repository, so they run one after the other rather than in parallel.

### Version PR body

The body of the version PR is version-pr's:

- It no longer lists the manifests that were updated.
- It says that merging creates the tag, the GitHub release and the floating
  tag. That only happens if your repository also runs the auto-tag workflow
  (`reusable-release-auto-tag.yml`), as before. Migrating does not set that
  up.
