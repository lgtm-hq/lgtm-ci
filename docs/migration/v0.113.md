# Upgrading to v0.113.0: harden-runner's eBPF fallback agent is refused unless you opt in

Applies to callers whose jobs get harden-runner's eBPF agent instead of its
standard agent (#1668). For most callers this happens only now and then,
when StepSecurity's TLS-status endpoint does not answer, and nothing needs
to change. A caller whose GitHub owner has StepSecurity TLS inspection
enabled gets the eBPF agent in every job, and those jobs fail until the
owner sets the variable below.

## What changed

The pinned harden-runner (v2.22.3) asks StepSecurity whether TLS inspection
is enabled for the repository owner before it installs its agent
(`src/tls-inspect.ts`). When the answer is yes, or the call fails or takes
more than 3 seconds, it installs the eBPF agent v1.9.5
(`step-security/agent-ebpf`) in place of the standard agent v0.18.0
(`step-security/agent`). A failed call prints
`[!] Unable to check TLS_STATUS. Defaulting to TLS enabled.`

The generated `Verify harden-runner agent` step, which follows every
harden-runner step in the reusables and examples, now trusts only the
standard agent by default. When it finds the eBPF agent, it fails the job at
its start with:

```text
harden-runner installed its eBPF fallback agent; only the standard agent is trusted
```

Before, such a job ran to its end and then failed in
`Recheck harden-runner agent` with "resolved.conf no longer uses the agent's
DNS proxy", because the eBPF agent enforces DNS in the kernel and never
changes resolved.conf.

When the TLS-status call merely failed, the failure is transient:
`reusable-auto-rerun-on-infra-failure.yml` re-runs the job once (attempt 1
only, when harden-runner's own fallback line proves the cause), and the
re-run usually gets the standard agent.

## Are you affected?

Your jobs fail at `Verify harden-runner agent` with the message above in
every run, including the automatic re-run, and harden-runner's pre-step
prints `[!] TLS_ENABLED: <owner>`. That means TLS inspection is enabled for
the owner, and harden-runner will always install the eBPF agent.

## What to do

Set a GitHub Actions configuration variable named
`LGTM_CI_ALLOW_HARDEN_RUNNER_EBPF_AGENT` to exactly `true`, on the
repository or on the organization (Settings, Secrets and variables, Actions,
Variables). Any other value, including `True` or `1`, keeps the eBPF agent
refused. No workflow input changes: the reusables read the variable through
the `vars` context, which inside a reusable workflow resolves to the
calling repository's variables.

An environment variable of that name overrides a repository variable, which
overrides an organization variable. An organization variable can be limited
to selected repositories (its "Repository access" policy), so check that the
repositories that need it can see it. GitHub's restrictions on
Dependabot-triggered runs cover only the `GITHUB_TOKEN` (read-only) and
secrets (only Dependabot secrets); configuration variables are not
restricted, so Dependabot pull requests read the same variable and need
nothing more. If a Dependabot run still fails at `Verify harden-runner
agent` with the refusal above, the variable was not visible to it: check the
organization variable's repository access, or set it on the repository.

With the variable set, the eBPF agent is accepted only with its own proof of
block mode, checked before any job step runs: its build record
(`[buildInfo] name=AgentAlpha …`) is the first record of `agent.log` and the
only build record (one agent start), every feature-flag line it writes says
`NetMode:ebpf`, its tracer logs `[tracerManager] block-policy applied`
within 30 seconds and no other policy line, `agent.service` is still active,
the policy lines still show block only after that, and the existing agent
checks (no revert, `egress_policy` block, subscription) pass. The step then
prints a warning saying the eBPF agent was accepted because of the variable.
Anything missing fails the job.

What the end-of-job recheck proves for the eBPF agent is narrower: the unit
is still active, and no other policy line and no revert line appeared in
`agent.log`. It does not prove the kernel still enforces the block policy,
because any job step can write `agent.log`. The revert check matches the
standard agent's messages; for the eBPF agent it relies on the same
`Reverted changes` and `Error in Initialization` strings being in its
binary, since its source is not public and no real eBPF log has shown a
revert, so treat it as not covering that agent
([workflow-contract.md](../workflow-contract.md), "Opting in to the eBPF
agent").

The trade-off: you rely on a second agent whose enforcement lgtm-ci checks
only through its own log, and whose recheck cannot see a step changing DNS
the way the standard agent's resolved.conf check can. Leave the variable
unset unless your owner needs TLS inspection.

If you copied `examples/publish-npm-set.yml` or
`examples/publish-python-release.yml`, copy them again: their verify and
recheck steps now pass the variable and the verified agent in `env:`, and
the recheck fails closed without them.
