# Migrating from v0.76.x to v0.77.0

This guide covers the caller-visible changes in v0.76.2 and v0.77.0, that is
everything merged after v0.76.1. The later v0.77.x patch releases change no
inputs, permissions or check names, so the checklist and sections 1 to 3
apply unchanged when you move straight to the latest v0.77.x. Two changes in
those patches are worth knowing:

- v0.77.1 promoted the recovery facade and its plan stage to `stable` (see
  [section 4](#4-other-changes-no-action-needed)).
- v0.77.3 moved `step-security/harden-runner` to v2.22.1. On the
  StepSecurity community tier it now enforces the egress policy on native
  Linux arm64 runners instead of skipping them. The default runners are
  x86-64 and unaffected; you only get arm64 runners by asking for one, through
  `runner-image`, `runner-map` or a Docker `matrix` `runner` entry. If those
  jobs reach hosts outside their allowlist, add the hosts to
  `allowed-endpoints`. If you rely on `egress-preset` alone, also set
  `allowed-endpoints-mode: append`, because on most reusables the default
  `replace` drops the preset.

The patches also bump pinned tool defaults and fix bugs; see
[CHANGELOG.md](../../CHANGELOG.md). Callers pin by SHA, so nothing changes
until you move the pin. The example below pins one v0.77.x release; use the
SHA of the tag you move to:

```yaml
uses: lgtm-hq/lgtm-ci/.github/workflows/<file>.yml@eae062ce40ce20fee8123f1ab609d4c5a57d8be2 # v0.77.0
```

## 1. Docker multi-platform check names gain a segment

Source: #1081.

**Who:** callers whose rulesets, branch protection or merge queue require a
check produced by `reusable-docker-multiplatform.yml`. That covers direct
calls and calls through `reusable-docker.yml` when `classify` picks the split
path (`runner-map`). No lgtm-hq ruleset requires one of these names (scanned
2026-10-09); single-platform and QEMU builds (`… / Docker build / …`) are
unchanged.

**Why:** the multi-platform facade now calls a read-only validate reusable
for `push: false` and an internal publish reusable for `push: true`, so a
validate-only caller can grant `contents: read` alone. GitHub prefixes each
nested job with the calling job's name, so every per-platform check gains
`Validate /` or `Publish /`.

**Change:** update required contexts as follows (`<job>` is your calling
job; through `reusable-docker.yml` the prefix is
`<job> / Docker multi-platform`).

<!-- markdownlint-disable MD013 -- wide mapping table -->

| Before | After |
| ------ | ----- |
| `<job> / Docker build per platform (<matrix values>)` | `push: false`: `<job> / Validate / Docker build per platform (<matrix values>)`; `push: true`: `<job> / Publish / Docker build per platform (<matrix values>)` |
| `<job> / Validation Summary` | `<job> / Validate / Validation Summary` |
| `<job> / Docker verify per platform (<matrix values>)` | `<job> / Publish / Docker verify per platform (<matrix values>)` |
| `<job> / Docker health check per platform (<matrix values>)` | `<job> / Publish / Docker health check per platform (<matrix values>)` |
| `<job> / Merge Manifests` | `<job> / Publish / Merge Manifests` |
| `<job> / Vulnerability Scan` | `<job> / Publish / Vulnerability Scan` |
| (none) | `<job> / Upload Trivy scan results (<matrix values>)`: new, only with `push: false` and `scan: true` (otherwise reported as skipped); uploads the validate path's SARIF to code scanning |

<!-- markdownlint-enable MD013 -->

The per-platform jobs have static names, so GitHub appends every value of
the matrix entry, in the matrix's key order, shown above as
`(<matrix values>)`. That order depends on who builds the matrix:

- Through `reusable-docker.yml`, the matrix is generated as platform,
  runner, slug, qemu. The fixture's `docker-orchestrator.yml` job `docker`
  reports `docker / Docker multi-platform / Validate / Docker build per
  platform (linux/amd64, ubuntu-24.04, linux-amd64, false)`.
- Calling `reusable-docker-multiplatform.yml` directly, it is your own
  matrix's key order. The fixture's `docker-facade-validate.yml` (platform,
  slug, runner, qemu) reports `facade / Validate / Docker build per platform
  (linux/amd64, linux-amd64, ubuntu-24.04, false)`.

Copy the exact contexts from a run of your own workflow into the ruleset.

The outputs, secrets and permission union of
`reusable-docker-multiplatform.yml` and `reusable-docker.yml` are
unchanged. Both gain one optional input, `artifact-prefix` (default
`docker`), which names the validate path's Trivy SARIF artifacts
(`<prefix>-trivy-sarif-<slug>`). Only a run that calls the multi-platform
path twice with `push: false` and `scan: true` needs distinct values.

## 2. Read-only entry points (no action needed)

Source: #1081. New, opt-in reusables a caller may switch to in order to
grant read scopes only. Their facades are unchanged apart from section 1.

<!-- markdownlint-disable MD013 -- wide table -->

| Facade | Read-only entry point | Caller grants |
| ------ | --------------------- | ------------- |
| `reusable-test-node.yml` | `reusable-test-node-run.yml` (since v0.76.1) | `actions: read`, `contents: read` |
| `reusable-test-shell.yml` | `reusable-test-shell-run.yml` | `actions: read`, `contents: read` |
| `reusable-rust-test.yml` | `reusable-rust-test-run.yml` | `actions: read`, `contents: read` |
| `reusable-docker-multiplatform.yml` | `reusable-docker-multiplatform-validate.yml` | `contents: read` |
| `reusable-release-recover.yml` | `reusable-release-recover-plan.yml` (dry run only) | `actions: read`, `contents: read` |

<!-- markdownlint-enable MD013 -->

See [Read-only variants](../reusable-workflows.md#read-only-variants) for
what each drops and how to post the PR comment or SARIF from a separate job.

## 3. Release recovery check names gain a segment

Source: #1081.

**Who:** anything keyed on a check name of `reusable-release-recover.yml`.
Recovery runs from a `workflow_dispatch` entry workflow, so a required
check is unlikely; no lgtm-hq ruleset requires one (scanned 2026-10-09).

**Why:** the facade now calls a read-only plan stage and an internal resume
stage, so a dry run can be made with read scopes only (section 2).

<!-- markdownlint-disable MD013 -- wide mapping table -->

| Before | After |
| ------ | ----- |
| `<job> / Resolve tag, artifacts, and channels` | `<job> / Plan / Resolve tag, artifacts, and channels` |
| `<job> / Resume npm channel` | `<job> / Resume / Resume npm channel` |
| `<job> / Resume GitHub Release channel` | `<job> / Resume / Resume GitHub Release channel` |
| `<job> / Re-dispatch Homebrew` | `<job> / Resume / Re-dispatch Homebrew` |
| `<job> / Record recovery outcome` | `<job> / Resume / Record recovery outcome` |

<!-- markdownlint-enable MD013 -->

Inputs, secrets and the permission union of `reusable-release-recover.yml`
are unchanged.

## 4. Other changes (no action needed)

Changes in v0.76.2 and v0.77.0 that a caller may notice but needs no edit for,
plus the v0.77.1 tier promotion noted inline.

- **Deprecations are recorded and gated** (#1133, #1082). Every deprecated
  input, output and entry point is listed in
  [catalog.md](../catalog.md#deprecations) with its replacement. The most
  common one is `tooling-ref`, which 61 reusables still accept and warn
  about. An item is removed only once no
  [known consumer](../governance.md#known-consumers) still uses it, or
  through a recorded exception that names the approving issue. Delete the
  optional `tooling-ref` from your calls when you move the pin, **except**
  on `reusable-release-recover.yml` and `reusable-release-recover-plan.yml`,
  where it stays required (set it to the same SHA as `uses:`). See
  [governance.md](../governance.md) for pinning and the removal rules.
- **New optional inputs:**
  - `catalog-release-notes` on `reusable-release-version-pr.yml` (default
    `false`), for repositories that keep an lgtm-ci support catalog.
  - `concurrency-scope` on `reusable-vuln-suppression-check.yml` (default
    empty: cleanup runs stay serialized per repository; #1139, v0.76.2). Set
    it, e.g. to `${{ github.ref }}`, only when runs on different refs must
    not supersede each other's queued run and none of them can open a
    cleanup PR at the same time as another.
- **Support tiers:** `reusable-docker-multiplatform`,
  `reusable-docker-multiplatform-validate` and `reusable-rust-test-run` are
  now `stable`. v0.77.0 shipped the recovery facade
  `reusable-release-recover` and its new plan stage
  `reusable-release-recover-plan` as `preview`; v0.77.1 promoted both to
  `stable`. The resume stage `reusable-release-recover-resume` is `internal`:
  call the facade.
- **Docker egress** (#1143): the `docker` preset now allows the hosts that
  `scan: true` (Trivy) and push-time provenance attestation (OIDC, Sigstore)
  reach, so these steps no longer fail under the default block mode. If
  you added those hosts through `allowed-endpoints`, you can drop them.
- **Pinned upstream actions** (#1118):
  - `actions/upload-artifact` v7.0.2 and `actions/download-artifact` v8.0.2
    honour `Retry-After` when rate-limited (HTTP 429).
  - `actions/setup-node` v7.1.0 retries the Node versions manifest fetch and
    runs `node --version` after installing, so a broken download fails in
    the setup step.
  - `github/codeql-action` v4.38.3 defaults to CodeQL 2.27.2.
  - `dtolnay/rust-toolchain` is the hardened `v1` (safer quoting of the
    toolchain input).
- **Tool version:** the default `cargo-nextest` is 0.9.148 (was 0.9.146)
  (#1152).
