# Comment formats (`comment-format`, #1678)

A caller picks how the test summary comment looks with `comment-format`.
Every format shows the same facts; a format changes layout and density only.

| Value               | Layout                                                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `classic` (default) | The comment as it has always been, byte for byte. An empty value means `classic`.                                                              |
| `compact`           | One headline line, the `comment-fields` on one line, and the rest in a **Details** section. The section is open when the result is not a pass. |
| `table`             | A heading with the status, then tables: the fields, one wide tests row, one coverage row. Nothing is folded but long lists.                    |

Any other value (`Compact`, `wide`, a trailing space) fails the publish job with
`unknown comment-format`; it never falls back to another format.

## Where it applies

`comment-format` is an input of `reusable-publish-test-summary.yml` and of every
workflow that calls it: `reusable-test-python.yml`, `reusable-test-node.yml`,
`reusable-test-node-custom.yml`, `reusable-test-shell.yml`,
`reusable-rust-test.yml`, `reusable-test-e2e-playwright.yml`,
`reusable-site-quality.yml` and `reusable-coverage.yml`.

```yaml
jobs:
  e2e:
    uses: lgtm-hq/lgtm-ci/.github/workflows/reusable-test-e2e-playwright.yml@<sha>
    permissions:
      contents: read
      pull-requests: write
    with:
      comment-format: compact
      comment-fields: |
        Environment: staging
        Environment URL: https://staging.example.com
        Region: eu-west-1
```

It lays out the test summary the workflow renders. A `prebuilt-test-summary-file`
and the rich coverage table (`rich-coverage-comment`, and the coverage comment
of `reusable-coverage.yml`) keep their own layout for now; the coverage, lint
and link-check comments get the same three shapes in later slices of #1678.
The run history (`comment-history`) is the same in every format.

## What every format shows

- **Counts.** Expected failures, unexpected passes and Other get a column (and
  a headline item) when they are above 0, as they get a row in `classic`; the
  pass rate names its denominator when it is not the total. Unexpected passes
  keep their note, and the expected failures their folded list with reasons,
  capped as in `classic` (200 characters a value, 20,000 bytes a list, the
  rest counted in "and N more").
- **Unreadable results** (#1692). When the counts could not be read or parsed,
  or the run was cut short, no count appears anywhere, the headline says
  `test counts unreadable`, `no test counts` or `results incomplete`, the
  table is replaced by the same notice `classic` shows, and the status is
  never a pass. A coverage value that is not a number reads `unreadable` with
  its notice.
- **Coverage.** The line coverage, the threshold and the verdict; the verdict
  drops `(>=80%)` because the threshold has its own column. Without
  `coverage-enabled` there is no coverage, as in `classic`.
- **Run facts.** The build verdict, the date, the commit (its first 8
  characters as the link text, the full SHA in the link) and the run link.
- **Comment fields.** The poster inserts them in the format's style: a
  quoted block (`classic`), one line under the headline (`compact`), a table
  under the heading (`table`). Rules: [comment-fields.md](comment-fields.md).

A row label in `compact` repeats the suite name; when the name is longer than
32 bytes or needs escaping, the label reads `this run` instead, so a format
never grows with the name more than `classic` does. Neither format is larger
than `classic` for the same data; the goldens test that for every case.

## The model (`comment.v1`)

`generate-test-summary.sh` still decides every fact: the status, the counts it
could read, the coverage verdict. For `compact` and `table` it passes those
decisions to `scripts/ci/lib/comment_test_report.py`, which arranges them into
one `comment.v1` document (`schemas/comment.v1.json`): a title, a status, the
headline groups, body blocks (tables, notices, folded lists), labelled facts,
links and a footer. `scripts/ci/lib/comment_format.py` lays that document out
in a format. Every string in the model is raw text: the formatter sanitises
each one for where it lands, with the shared sanitiser
([comment-sanitize.md](comment-sanitize.md)). The `classic` layout is not
produced from the model; it stays each renderer's own markdown. Set
`COMMENT_MODEL_OUTPUT` on `generate-test-summary.sh` to write the model it
built beside the comment.

`scripts/ci/workflows/validate_comment_format_forwarding.py` fails when a
workflow calls one that declares `comment-format` without declaring and
forwarding it, or when the publisher does not pass it to the steps that check
and render it.
